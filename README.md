# Mini Git — 자료구조와 알고리즘으로 구현한 CLI 버전 관리 시스템

Python 3.10+로 개발한 **학습용 Mini Git** 프로젝트. 실제 Git의 커밋 관계, 브랜치 HEAD, 로그 조회 및 그래프 탐색을 파일 추적 없이 **메모리 기반으로 구현**했다.

> **범위:** 커밋의 메타데이터(해시 식별자, 메시지, 작성자, 시각, 부모 해시)만 다룬다. 실제 Git의 파일 버전 관리, 원격 저장소 통신, 영구 저장, 실제 SHA 해시 생성은 구현 범위 밖이다.

## 1. 실행 방법

Mac / Linux에서 프로젝트 폴더를 VS Code로 열고 터미널을 실행한다.

**Mac 터미널 (예: `Mini_Git %`):**

```bash
python3 --version
python3 main.py
```

**Mini Git 프로그램 (화면에 `mini-git>` 표시):** 여기에서 `INIT`, `COMMIT`, `LOG` 같은 명령을 입력한다.

```text
mini-git> INIT Alice
mini-git> COMMIT "Initial commit"
mini-git> BRANCH feature
mini-git> SWITCH feature
mini-git> COMMIT "Add login feature"
mini-git> SWITCH main
mini-git> COMMIT "Add payment feature"
mini-git> PATH 00000002 00000003
mini-git> ANCESTORS 00000003
mini-git> SEARCH login
mini-git> SEARCH --author=Alice
mini-git> LOG
mini-git> LOG --sort-by=date
mini-git> LOG --sort-by=author
mini-git> STATUS
mini-git> exit
```

위 예시의 `PATH 00000002 00000003` 결과는 `00000002 -> 00000001 -> 00000003` 경로가 된다.

**주의:** `[main 00000001] Initial commit` 같은 문구는 프로그램의 **출력 결과**이지 입력 명령이 아니다. 프로그램을 종료했다가 다시 실행하면 모든 저장소 데이터가 초기화된다. 새 실행에서 같은 예시를 처음부터 입력해야 한다.

## 2. 구현 명령어

| 명령 | 역할 | 구현 핵심 |
|---|---|---|
| `INIT <user_name>` | 현재 작성자, main 브랜치 및 빈 저장소 설정 | 딕셔너리 초기화 |
| `COMMIT "<message>"` | 고유 ID를 발급하고 현재 HEAD를 부모로 커밋 추가 | 커밋 객체, DAG, 역색인 갱신 |
| `BRANCH <branch_name>` | 현재 HEAD를 가리키는 새 브랜치 생성 | 딕셔너리 |
| `SWITCH <branch_name>` | 현재 작업 브랜치 변경 | 브랜치 포인터 |
| `LOG` | **부모 먼저, 자식 나중** 순서로 모든 커밋 출력 | DFS 기반 위상 순서 |
| `LOG --sort-by=date` | 작성 시각 오름차순 정렬 | 직접 구현한 병합 정렬 |
| `LOG --sort-by=author` | 작성자 이름 오름차순 정렬(대소문자 무시) | 직접 구현한 병합 정렬 |
| `PATH <hash1> <hash2>` | 무방향 부모·자식 간선의 최단 경로 출력 | BFS |
| `ANCESTORS <hash>` | 해당 커밋보다 앞선 모든 조상 검색 | DFS |
| `SEARCH <keyword>` | 메시지에서 일치 단어 검색 | 키워드 역색인 |
| `SEARCH --author=<name>` | 작성자 이름으로 검색 | 작성자 역색인 |
| `STATUS` | 현재 브랜치, HEAD, 전체 커밋 수 | 학습 편의 명령 |
| `exit` / `quit` | 프로그램 종료 | REPL 종료 |

명령어 이름은 대소문자를 구분하지 않는다. 인자의 공백은 따옴표로 묶는다(예: `INIT "Alice Smith"`, `SEARCH --author="Alice Smith"`). 지원하지 않는 명령은 `Unknown command`, 잘못된 인자 형식은 `Invalid args`를 출력한다.

### 커밋 데이터 예시

```text
commit 00000003 (Alice, 2026-11-08 16:09:15)
Parents: 00000001
Add payment feature
```

`Commit` 데이터클래스의 필드: `hash`, `message`, `author`, `timestamp`, `parents`.

실제 Git의 해시는 콘텐츠를 바탕으로 만들지만 이 프로젝트는 **세션 내 증가하는 정수의 8자리 16진수 표현**을 사용한다. 예: `00000001`, `00000002`. 따라서 실제 Git의 SHA와 동일하다고 주장하면 안 된다.

## 3. 커밋 그래프와 브랜치

```text
          00000001 (Initial)
           /             \
          v               v
   00000002 (feature)  00000003 (main)
```

새 커밋은 존재하는 현재 브랜치 HEAD를 부모로 지정한다. 부모로부터 자식으로 바라보면 **방향이 있는 비순환 그래프(DAG)**다. 각 노드는 `parents` 목록으로 이전 커밋을 가리킨다. 이 때문에 브랜치 전환 시 커밋을 복사하지 않고 `branches[branch_name]`의 HEAD를 읽기만 하면 된다.

- `main`과 `feature`는 서로 다른 HEAD를 가질 수 있다.
- `SWITCH`는 커밋을 옮기지 않는다. 브랜치를 바꿀 뿐이다.
- 커밋은 `dict[hash, Commit]`에 저장한다. 해시로 커밋을 찾는 작업은 **평균 O(1)**이다.
- 여러 브랜치의 공통 조상이 있을 수 있다.
- 첫 커밋이 생성되기 전에 서로 다른 빈 브랜치를 만들면 각각 **별도 루트**가 생길 수 있다. 이 경우 `PATH`는 `No path`를 출력한다.
- 데이터 모델에는 다중 부모를 담을 수 있지만, **MERGE 명령은 구현하지 않았다**.

## 4. 알고리즘 선택 이유

### DFS(깊이 우선 탐색): LOG 및 ANCESTORS

**LOG:** 커밋을 방문하기 전에 먼저 부모 커밋을 재귀적으로 방문한다. 그래서 출력에선 반드시 **부모가 자식보다 앞**에 나온다. 같은 부모에서 갈라진 서로 다른 자식 간 상대 순서는 제한하지 않는다. 순환 또는 존재하지 않는 부모를 탐지하도록 구현했다.

**ANCESTORS:** 지정한 커밋의 부모에서 시작해 스택을 이용한 DFS를 수행한다. 이미 방문한 조상은 `set`으로 중복 방지한다. **시작 커밋 자신은 포함하지 않는다.** 출력 편의를 위해 수집한 조상 해시 목록을 직접 구현한 삽입 정렬로 정렬한다.

### BFS(너비 우선 탐색): PATH

`PATH`에서 부모 관계는 **양방향 간선**으로 취급한다. 목적지에서 BFS를 수행하여 각 커밋까지의 최소 거리를 계산한 뒤, 출발지에서 목적지까지 **남은 거리가 1씩 줄어드는 이웃**을 따라간다. 동일 길이의 최단 경로가 여러 개일 때는 그중 **사전순으로 작은 해시**를 선택한다. 연결되지 않으면 `No path`다.

### 역색인(Inverted Index): SEARCH

커밋 생성 시 메시지를 **공백 기준으로 분리하고 소문자로 변환**하여 각 단어가 속한 커밋 해시를 색인한다. 작성자도 소문자로 색인한다.

```text
login  -> [00000002, 00000004]
fix    -> [00000004]
alice  -> [00000001, 00000002, 00000004]   (작성자 색인)
```

이 방식은 조회할 때마다 전체 커밋을 순회하지 않아도 되는 장점이 있다. 동일 메시지 안의 같은 단어는 **한 번만 색인**한다. `INIT` 재실행 시 커밋 저장소와 역색인을 **함께 초기화**한다.

**검색 범위:** 정확히 일치하는 **단어** 기준이다. 예를 들어 `login`은 `login`과 일치하지만 `login!`과는 일치하지 않는다. 부분 문자열/형태소 검색은 지원하지 않는다.

### 병합 정렬(Merge Sort): LOG --sort-by

`sorting.py`에 **재귀적 병합 정렬**을 구현했다. 리스트를 반으로 나누고 각각 정렬한 뒤 두 정렬 결과를 병합한다. `sorted()`, `.sort()`를 사용하지 않는다.

- `date`: 타임스탬프 오름차순, 같으면 해시 오름차순.
- `author`: 작성자 이름을 소문자로 비교해 오름차순, 같으면 해시 오름차순.
- 정렬 옵션을 사용한 LOG는 날짜 또는 작성자 기준이 우선하므로, **기본 LOG의 부모 우선 순서를 보장하는 모드는 아니다.**
- 현재 CLI는 `INIT` 시점에 작성자를 하나 정하고, 커밋별 작성자를 바꾸는 별도 명령은 제공하지 않는다. 여러 작성자 정렬은 자동 테스트에서 확인한다.

## 5. 시간·공간 복잡도

`V`는 커밋 수, `E`는 부모·자식 연결 수, `K`는 검색 결과 수, `A`는 조상 수라고 하자.

| 작업 | 시간 복잡도 | 설명 |
|---|---|---|
| 해시로 커밋 조회 | 평균 O(1) | 딕셔너리 사용 |
| BRANCH / SWITCH | 평균 O(1) | 딕셔너리 조회·갱신 |
| LOG 기본 | O(V + E) | DFS |
| PATH | O(V + E) | 인접 리스트 구성 + BFS + 경로 복원 |
| ANCESTORS | O(V + E + A²) 상한 | DFS 후 삽입 정렬 |
| LOG 날짜/작성자 정렬 | O(V + E + V log V) | 부모 우선 DFS 후 병합 정렬 |
| SEARCH 조회 | 평균 O(K) | 딕셔너리 인덱스 조회 후 결과 출력 |

병합 정렬의 추가 공간은 **O(V)** 수준이고, 경로 탐색은 인접 목록과 거리 저장을 위해 **O(V + E)** 수준의 추가 공간을 사용한다. 위 표는 일반적인 해시 테이블의 평균 성능과 구현 방식에 근거한 분석이며, 사용자 입력·출력 문자열 처리 비용은 단순화했다.

## 7. 테스트 및 검증 방법

**입력 위치: Mac 터미널 (`Mini_Git %`)** — `mini-git>` 프로그램 내부에서는 실행하지 않는다.

```bash
python3 -m unittest discover -s tests -v
```

자동 테스트 범위:

1. INIT 및 커밋 부모/작성자/HEAD 기록
2. 브랜치 독립성과 빈 브랜치
3. 부모 우선 LOG, 다중 브랜치, 빈 로그

5. 조상 검색, 다중 부모, 중복 조상 제거
6. 키워드·작성자 역색인, 대소문자, 반복 단어, INIT 재실행
7. 날짜·작성자 정렬, 동률, 빈 저장소, 병합 정렬 안정성
8. 잘못된 명령어, 인자 부족, 잘못된 따옴표, 명령어 대소문자

## 8. 제약과 미구현 범위

- **세션 메모리 저장**: 프로그램을 종료하면 기록이 사라짐.
- **실제 파일 관리 미지원**: 스테이징, 파일 변경 추적, 파일 복원 등은 구현하지 않음.
- **학습용 해시**: 실제 SHA 콘텐츠 해시가 아닌 8자리 증가 ID.
- **작성자 변경 명령 미지원**: 한 INIT 세션 내 일반 CLI 커밋은 모두 같은 작성자.
- **보너스 기능 미구현**: MERGE 명령, DIFF, 정렬 알고리즘 성능 비교.
- **Python 3.10 이상 권장**: `str | None` 타입 표기 등을 사용.

## 9. 처음 배우는 사람을 위한 해설: 왜 이 자료구조와 알고리즘을 선택했을까?

이 미션의 가장 중요한 학습 목표는 **명령어가 작동하는 것에서 끝나지 않고, 어떤 문제를 해결하려고 그 기술을 선택했는지 설명하는 것**이다.

어려운 용어를 먼저 외우지 말고 아래 순서로 이해해 보자.

> **문제 → 필요한 작업 → 선택한 자료구조/알고리즘 → 실제 코드 → 선택 이유**

### 9-1. 먼저, 자료구조와 알고리즘의 차이

- **자료구조(Data Structure)**: 데이터를 어떤 모양으로 보관할지 정하는 방식이다. 책을 책장에 꽂는 규칙이라고 생각하면 된다.
- **알고리즘(Algorithm)**: 보관된 데이터를 어떤 순서와 방법으로 처리할지 정하는 절차다. 원하는 책을 찾는 방법이라고 생각하면 된다.

Mini Git에서는 **커밋 기록을 그래프로 보관**하고, **필요한 커밋을 BFS나 DFS로 탐색**한다. 즉, *어떻게 저장할지*와 *어떻게 찾을지*가 서로 연결된다.

### 9-2. 왜 커밋을 그래프(DAG)로 만들었을까?

**문제:** 처음 커밋에서 `main`과 `feature` 브랜치가 갈라질 수 있다. 커밋을 단순한 직선 목록으로만 생각하면 어느 커밋이 누구의 부모인지 표현하기 어렵다.

```text
00000001  Initial commit
   ├── 00000002  Add login feature   (feature)
   └── 00000003  Add payment feature (main)
```

- **그래프(Graph)**는 점(노드)과 점을 연결하는 선(간선)으로 관계를 표현한다.
- 여기서 **노드 = 커밋**, **간선 = 부모와 자식의 관계**다.
- **DAG(Directed Acyclic Graph)**는 방향이 있고, 연결을 따라가도 출발점으로 되돌아오는 순환이 없는 그래프다.
- 커밋을 생성할 때는 기존 HEAD가 새 커밋의 부모가 된다. 기존 커밋은 미래에 생길 커밋을 부모로 갖지 않으므로 정상적인 생성 과정에서 순환이 생기지 않는다.

**왜 선택했나?** 브랜치가 여러 개로 갈라져도 공통 부모, 커밋 이력, 조상 관계를 자연스럽게 표현할 수 있기 때문이다.

**어디에 구현했나?** `commit.py`의 `parents` 필드와 `mini_git.py`의 `commit()`, `branch()`, `switch()` 메서드다.

**주의:** 이 프로젝트의 `SWITCH`는 현재 브랜치 포인터만 변경한다. 실제 파일 내용은 전환하지 않는다.

### 9-3. 왜 딕셔너리(HashMap)를 사용했을까?

**문제:** 커밋이 수천 개 있을 때 `00000042`라는 해시를 가진 커밋을 찾는다고 해보자. 목록의 첫 번째부터 마지막까지 매번 확인하면 비효율적이다.

**해결:** 해시 문자열을 열쇠(key), 커밋 객체를 값(value)으로 넣는 딕셔너리를 사용한다.

```python
self.commits = {
    "00000001": Commit(...),
    "00000002": Commit(...),
}
commit = self.commits["00000002"]
```

위 코드는 개념을 보여주는 예시이며 실제 생성 코드는 `mini_git.py`의 `commit()`에 있다.

- **HashMap/딕셔너리**: 열쇠로 원하는 데이터를 빠르게 꺼내는 자료구조다.
- **평균 O(1)**: 커밋 수가 늘어나도 해시 조회 한 번에 드는 평균 비용이 크게 늘지 않는다는 뜻이다. 항상 정확히 1단계라는 의미는 아니다.
- **왜 선택했나?** `PATH`, `ANCESTORS`, `LOG` 등이 커밋 해시로 커밋 객체를 자주 조회하기 때문이다.
- **어디에 구현했나?** `mini_git.py`의 `self.commits`, `self.branches`다.

여기서 혼동하지 말 것: **커밋의 hash는 식별자**, **HashMap은 식별자로 데이터를 찾는 보관 방법**이다. 현재 해시는 SHA가 아니라 증가하는 숫자를 16진수 문자열로 표현한 것이다.

### 9-4. 왜 DFS를 LOG와 ANCESTORS에 사용했을까?

**문제 A — `LOG`:** 부모 커밋이 항상 자식보다 **먼저** 출력돼야 한다.

DFS(Depth-First Search, 깊이 우선 탐색)는 한 방향으로 가능한 만큼 들어갔다가 되돌아오는 탐색 방식이다. 이 프로젝트에서는 **부모를 먼저 방문한 다음 자기 자신을 출력**하도록 했다.

```text
00000001 ─┬─> 00000002
          └─> 00000003

LOG 출력 예: 00000001 → 00000002 → 00000003
```

부모를 먼저 처리하므로 `00000001`이 자식보다 앞에 나온다. 이것이 이 미션에서 요구하는 **위상 정렬 성격의 순서**다. 형제 커밋 사이의 순서까지 반드시 고정할 필요는 없다.

**문제 B — `ANCESTORS 00000003`:** 특정 커밋의 부모를 따라 계속 올라가 조상을 모두 찾아야 한다.

DFS는 부모 → 그 부모의 부모 → 그 위의 부모를 차례로 방문하기에 잘 맞는다. 방문한 조상은 `set`으로 기록해 중복 탐색을 막는다.

- **왜 선택했나?** `LOG`는 부모 우선 순서, `ANCESTORS`는 모든 상위 커밋 방문이 목적이기 때문이다.
- **어디에 구현했나?** `graph.py`의 `parent_first()`(재귀 DFS), `ancestors()`(스택 DFS)다.
- **꼭 알아둘 점:** DFS가 모든 문제의 최단 경로를 보장하지는 않는다. 그래서 `PATH`에는 다른 알고리즘을 쓴다.

### 9-5. 왜 PATH에는 DFS가 아니라 BFS를 사용했을까?

**문제:** `PATH 00000002 00000004`에서 커밋 사이를 이동하는 **가장 짧은 경로**가 필요하다.

```text
00000002 ─ 00000001 ─ 00000003 ─ 00000004
   시작                                도착
```

- **DFS**는 한쪽 길을 끝까지 탐색한다. 경로를 찾을 수는 있지만, 처음 찾은 경로가 가장 짧다는 보장은 없다.
- **BFS(Breadth-First Search, 너비 우선 탐색)**는 출발점으로부터 한 칸 거리, 두 칸 거리, 세 칸 거리 순서로 넓게 확인한다. 모든 간선의 이동 비용이 같다면 최단 거리를 보장한다.
- 이 프로젝트의 `PATH`는 부모·자식 연결을 **양방향**으로 취급한다. 실제 저장된 부모 링크의 방향만 따라가는 탐색과 다르다.
- 구현에서는 **목적지에서 BFS로 거리표를 만든 다음**, 출발지부터 거리가 줄어드는 이웃을 택한다. 같은 길이의 경로가 여러 개면 해시 사전순으로 가장 작은 경로를 고른다.

**왜 선택했나?** `PATH`는 방문 자체가 아니라 **최단 거리**가 정답이기 때문이다.

**어디에 구현했나?** `graph.py`의 `shortest_path()`와 `mini_git.py`의 `path()`다.

**기억할 문장:** **“전체 조상을 찾는 것은 DFS, 최단 경로를 찾는 것은 BFS.”** 단, 이는 이 Mini Git에서 선택한 방법을 쉽게 기억하기 위한 설명이지, 모든 프로그램에서 반드시 그래야 한다는 규칙은 아니다.

### 9-6. 왜 SEARCH에는 역색인(Inverted Index)을 사용했을까?

**문제:** `SEARCH login`을 실행할 때마다 모든 커밋 메시지를 처음부터 읽으면 커밋이 많아질수록 오래 걸린다.

검색을 빠르게 하기 위해 **커밋을 생성할 때 미리 단어별 목록을 만들어 둔다.**

```text
커밋 기록:
00000001: Initial commit
00000002: Add login feature
00000003: Fix login error

미리 만든 역색인:
login → [00000002, 00000003]
fix   → [00000003]
```

- 일반적인 저장은 `커밋 → 메시지` 방향이다.
- **역색인**은 거꾸로 `단어 → 그 단어가 포함된 커밋 목록` 방향으로 보관한다.
- 검색 시 전체 커밋을 확인할 필요 없이 해당 단어에 연결된 커밋을 조회한다.
- `SEARCH --author=Alice`도 작성자별 역색인으로 조회한다.

**왜 선택했나?** 미리 색인을 만드는 비용을 지불하는 대신, 반복되는 검색을 빠르게 처리하기 위해서다.

**어디에 구현했나?** `inverted_index.py`의 `add()`, `keyword()`, `author()`와 `mini_git.py`의 `commit()`, `search()`다.

**한계:** 메시지를 공백 기준으로 나눠서 정확히 일치하는 단어만 검색한다. `login`과 `login!`은 다른 단어로 처리한다.

### 9-7. 왜 LOG 정렬에는 병합 정렬(Merge Sort)을 선택했을까?

**문제:** `LOG --sort-by=date`와 `LOG --sort-by=author`는 커밋을 날짜·작성자 순서로 배열해야 한다. 그런데 미션에서는 Python의 `sorted()`, `.sort()` 사용이 금지돼 있다.

**병합 정렬**은 자료를 반씩 나누고 각각 정렬한 다음, 정렬된 두 목록을 하나로 합치는 방식이다.

```text
원래 순서: [3, 1, 4, 2]
          /          \
      [3, 1]       [4, 2]
      /   \         /   \
     [3]  [1]     [4]  [2]
       \  /         \  /
       [1, 3]      [2, 4]
           \       /
          [1, 2, 3, 4]
```

- **왜 선택했나?** 내장 정렬 함수 없이 직접 구현 가능하고, 데이터가 많아져도 비교적 일정한 성능인 **O(n log n)**을 보장하기 때문이다.
- **어디에 구현했나?** `sorting.py`의 `merge_sort()`와 `mini_git.py`의 `log()`다.
- **주의:** `LOG` 기본 모드는 부모 우선 순서지만, `--sort-by` 옵션을 붙이면 날짜·작성자 기준이 우선이므로 부모 우선 출력이 유지된다는 보장은 없다.

### 9-8. O(1), O(n), O(n log n)은 무슨 뜻일까?

**시간복잡도**는 실제로 몇 초 걸렸는지가 아니라, **데이터가 많아질 때 처리해야 할 작업량이 얼마나 늘어나는지** 나타내는 개념이다.

| 표기 | 쉬운 뜻 | Mini Git 예시 |
|---|---|---|
| `O(1)` | 데이터 수가 늘어도 평균 조회 비용이 거의 일정 | 딕셔너리로 해시 조회 |
| `O(n)` | 데이터 수에 비례해 작업이 증가 | 커밋 목록을 한 번 훑기 |
| `O(V + E)` | 커밋과 연결선을 한 번씩 살펴보는 수준 | 기본 LOG의 DFS, PATH의 BFS |
| `O(n log n)` | 자료를 반복해서 절반으로 나누며 정렬 | 병합 정렬 |
| `O(n²)` | 데이터가 커지면 작업이 더 빠르게 증가 | 최악의 경우 삽입 정렬 |

**예를 들어** 커밋이 100개에서 1,000개로 늘어날 때, 전체 목록 탐색은 대략 처리 대상도 10배가 되지만, 딕셔너리의 평균 단일 해시 조회는 10배로 늘어나지 않는다.

### 9-9. 발표나 평가에서 이렇게 설명하면 된다

**Q. 왜 Git 커밋을 배열이 아닌 그래프로 표현했나?**

A. “브랜치는 한 커밋에서 여러 방향으로 갈라질 수 있습니다. 따라서 부모와 자식 관계를 표현하기 쉬운 DAG를 사용했습니다. 각 커밋은 부모 해시 목록을 가지고 있습니다.”

**Q. 왜 딕셔너리를 사용했나?**

A. “커밋을 해시로 빠르게 찾기 위해서입니다. 리스트에서 처음부터 찾는 것보다 딕셔너리의 평균 O(1) 조회가 유리합니다.”

**Q. DFS와 BFS를 왜 구분했나?**

A. “LOG는 부모를 먼저 출력해야 하고 ANCESTORS는 모든 조상을 찾는 작업이라 DFS를 사용했습니다. PATH는 최단 경로가 필요하므로 BFS를 사용했습니다.”

**Q. 역색인은 무엇이 좋은가?**

A. “검색할 때 모든 커밋을 매번 읽는 대신, 커밋을 만들 때 단어별 목록을 저장해 빠르게 조회할 수 있습니다.”

**Q. 병합 정렬을 선택한 이유는?**

A. “미션에서 내장 정렬 함수 사용을 금지했기 때문에 정렬 알고리즘을 직접 구현했습니다. 병합 정렬은 O(n log n)의 시간복잡도를 보장해 선택했습니다.”

**한 문장으로 정리:** “Mini Git은 커밋의 관계를 **DAG**, 빠른 조회를 **딕셔너리**, 부모·조상 탐색을 **DFS**, 최단 경로를 **BFS**, 검색을 **역색인**, 정렬을 **병합 정렬**로 해결한 프로젝트입니다.”

## 11. B5-2 평가 체크리스트 답변: 항목 2 · 3 · 4

이 절은 **실제 Mini Git 구현 코드**를 기준으로 작성한 평가 대비 해설이다. 질문의 순서는 B5-2 체크리스트 원문과 같다.

### 항목 2. 자료구조와 코드 설계 (5문항)

#### 2-1. 커밋 저장소·브랜치·HEAD·사용자 정보는 어떻게 분리했나?

**답변:** 한 클래스에서 모든 기능을 처리하되, 서로 역할이 다른 정보를 다른 변수와 파일로 구분했다.

| 정보 | 실제 저장 구조 | 역할 |
|---|---|---|
| 커밋 데이터 | `MiniGit.commits: dict[str, Commit]` | hash를 열쇠로 커밋 객체 검색 |
| 브랜치 | `MiniGit.branches: dict[str, str | None]` | 브랜치 이름에 해당하는 최신 커밋(HEAD) hash 저장 |
| 현재 브랜치 | `MiniGit.current_branch: str` | 지금 선택한 브랜치 이름 |
| 현재 사용자 | `MiniGit.author: str` | 새 커밋의 작성자 |
| 초기화 여부 | `MiniGit.initialized: bool` | INIT 없이 명령어 실행하는 오류 방지 |
| 커밋 식별 번호 | `MiniGit.next_commit_id: int` | 다음 커밋의 고유 번호 생성 |
| 검색 색인 | `MiniGit.index: InvertedIndex` | 작성자·키워드 검색에 필요한 역색인 |

**HEAD를 따로 커밋으로 저장하지 않는 이유:** 현재 브랜치 이름 `current_branch`를 알면 `branches[current_branch]`가 바로 현재 HEAD이기 때문이다. 같은 정보를 중복 저장하지 않아 불일치를 줄였다.

**파일별 역할:** `commit.py`는 커밋 데이터, `mini_git.py`는 저장소 상태와 명령 기능, `main.py`는 사용자 입력 분석, `graph.py`는 탐색 알고리즘, `sorting.py`는 정렬 알고리즘, `inverted_index.py`는 검색 색인을 담당한다.

#### 2-2. 커밋 hash 조회는 어떻게 빠르게 하고, 중복·충돌은 어떻게 방지했나?

**답변:** `dict[hash, Commit]`을 사용하므로 hash로 조회할 때 평균 O(1)의 시간이 걸린다.

`mini_git.py`의 `commit()`에서는 아래처럼 번호를 만든다.

```python
commit_hash = f"{self.next_commit_id:08x}"
self.next_commit_id += 1
```

예를 들어 1 → `00000001`, 2 → `00000002`, 10 → `0000000a`가 된다. 같은 INIT 세션에서 증가 번호를 재사용하지 않기 때문에 **현재 CLI를 통한 정상 생성 경로에서는 중복이 발생하지 않는다.** 브랜치를 바꿔도 공통 카운터를 사용한다.

**중요한 한계:** 현재 코드는 해시가 이미 `self.commits`에 있는지 검사하는 별도 충돌 처리, 임의의 외부 커밋 삽입, 영구 저장 후 카운터 복구 기능은 구현하지 않았다. 따라서 “모든 상황에서 충돌을 탐지한다”고 주장하면 안 된다. 실제 Git의 콘텐츠 기반 SHA 해시와도 다르다.

#### 2-3. 커밋 생성 시 역색인은 언제, 어떻게 갱신하나?

**답변:** `COMMIT`이 새 커밋을 만든 직후, `mini_git.py`에서 `self.commits[commit_hash] = new_commit` 다음에 `self.index.add(commit_hash, message, self.author)`를 실행한다.

`inverted_index.py`에서는 메시지를 공백으로 나누고 각 단어를 소문자로 바꾼 뒤 `단어 → [커밋 해시]` 형태로 저장한다. 작성자도 소문자로 바꿔 `작성자 → [커밋 해시]` 목록에 넣는다. `set`을 이용하므로 메시지에 같은 단어가 여러 번 나와도 해당 커밋은 한 번만 색인된다.

```text
COMMIT "Add login login"
  ↓ 커밋 저장
  ↓ login → [새 커밋 hash] (한 번만 추가)
  ↓ add   → [새 커밋 hash]
  ↓ alice → [새 커밋 hash] (작성자 색인)
  ↓ 브랜치 HEAD 갱신
```

**왜 생성 시점에 갱신하나?** 검색할 때마다 전체 커밋 메시지를 읽는 대신 이미 만들어진 색인에서 바로 찾기 위해서다. `INIT`을 다시 실행하면 커밋과 색인을 함께 초기화한다.

#### 2-4. LOG·PATH·ANCESTORS의 그래프 탐색 코드는 어떻게 재사용 가능하게 구성했나?

**답변:** 사용자 인터페이스와 탐색 알고리즘을 분리했다.

- `main.py`는 명령어와 인자를 해석한다.
- `mini_git.py`는 커밋 유효성을 확인하고 결과 문자열을 만든다.
- `graph.py`는 화면 출력과 독립적으로 `parent_first(commits)`, `shortest_path(commits, start, end)`, `ancestors(commits, hash)`를 제공한다.

따라서 `graph.py`의 함수들은 CLI가 아니어도 테스트 코드에서 직접 호출할 수 있다. **재사용한다는 뜻은 세 기능이 무조건 하나의 탐색 함수를 쓴다는 뜻이 아니라, 그래프 처리 로직을 별도 모듈로 분리해 다른 코드에서도 쓸 수 있다는 뜻**이다.

#### 2-5. docstring과 주석은 어떤 기준으로 작성했나?

**답변:** 코드가 *무엇을 하는지*는 함수의 docstring으로, *왜 특별한 처리를 하는지*는 주석으로 설명한다. 실제로 `parent_first()`에는 부모 우선 순서, `shortest_path()`에는 무방향 최단 경로와 사전순 동률 규칙, `merge_sort()`에는 정렬 기준과 복잡도가 docstring으로 들어 있다.

- 함수명과 코드만 봐도 알 수 있는 단순 동작은 중복 설명을 줄인다.
- 사이클 검사, 사전순 경로 선택, 내장 정렬 함수 금지 같은 **요구사항과 연결되는 판단**을 우선 기록한다.
- 코드가 변경되면 docstring과 README도 함께 갱신한다.

현재 주석이 모든 코드 줄을 설명하지는 않는다. 그 대신 **목적·예외·설계 이유**를 중심으로 작성했다.

### 항목 3. 자료구조·알고리즘 원리 (5문항)

#### 3-1. 왜 DAG여야 하나? 사이클이 생기면 무엇이 문제인가?

커밋은 과거의 커밋을 부모로 가리키는 구조다. 만약 `A → B → C → A`처럼 순환이 생기면 A를 출력하기 전에 B가 필요하고, B 전에 C가 필요하고, C 전에 다시 A가 필요하므로 **부모 우선 LOG 순서를 정할 수 없다.** 또 조상 탐색에서 방문 여부를 관리하지 않으면 무한 반복할 수 있다.

현재 `COMMIT`은 존재하는 HEAD만 부모로 삼아 새로운 커밋을 만들기 때문에 정상적인 생성 과정에서 순환이 생기지 않는다. `graph.py`의 `parent_first()`는 방문 중인 노드를 다시 방문하면 `ValueError`를 발생시킨다.

#### 3-2. LOG에서 부모 먼저 조건은 어떻게 구현했나?

`graph.py`의 `parent_first()`에서 **부모를 재귀 DFS로 먼저 처리한 다음 현재 커밋을 결과 목록에 추가**한다. 이 방식은 DAG에 대해 위상 정렬의 한 순서를 만든다.

```text
A (부모)
├── B (자식)
└── C (자식)

허용 순서: A, B, C 또는 A, C, B
금지 순서: B, A, C (자식 B가 부모 A보다 먼저 나옴)
```

형제 B와 C는 서로 선후 관계가 없으므로 순서가 달라도 된다. 일반 `LOG`만 이 조건을 보장하며 `LOG --sort-by=author` 등의 별도 정렬은 현재 이 조건을 유지하지 않는다.

#### 3-3. PATH에 왜 BFS를 썼고, 왜 간선을 무방향으로 취급하나?

**BFS**는 가까운 노드부터 탐색하므로 각 간선의 비용이 같을 때 최단 거리를 계산할 수 있다. 이것이 DFS보다 `PATH`에 적합한 이유다.

문제에서 **커밋과 부모 사이의 연결을 무방향 간선으로 간주**하라고 요구했다. 따라서 현재 커밋에서 부모뿐 아니라 자식 방향으로도 이동할 수 있어야 한다.

```text
A (공통 부모)
├── B (feature)
└── C (main)

PATH B C = B → A → C
```

`graph.py`의 `shortest_path()`는 부모·자식 양쪽의 인접 목록을 만든 다음 **목적지에서 BFS 거리 계산**, 이후 **출발지에서 거리가 줄어드는 이웃 선택**으로 경로를 복원한다. 최단 경로가 여러 개면 hash가 사전순으로 작은 이웃을 선택하도록 했다.

#### 3-4. 정렬 알고리즘의 평균·최악 시간복잡도와 안정 정렬 여부는?

이번 프로젝트에서 실제 사용한 **병합 정렬(Merge Sort)**은 데이터를 계속 절반으로 나눠 정렬된 두 목록을 합친다.

| 알고리즘 | 평균 | 최악 | 안정 정렬 | 이번 코드 |
|---|---|---|---|---|
| 병합 정렬 | O(n log n) | O(n log n) | 예 | `sorting.py`의 `merge_sort()` |
| 삽입 정렬 | O(n²) | O(n²) | 예(일반적인 구현) | `graph.py`의 조상 해시 정렬 |
| 선택 정렬 | O(n²) | O(n²) | 일반적으로 아니오 | 비교용 설명, 미구현 |
| 퀵 정렬 | O(n log n) | O(n²) | 일반적으로 아니오 | 비교용 설명, 미구현 |

**안정 정렬**은 **정렬 기준이 같은 값들의 원래 순서**를 유지하는 것이다. `sorting.py`는 양쪽 값이 같을 때 왼쪽 데이터를 먼저 병합(`<=`)하므로 안정 정렬이다.

다만 실제 `LOG --sort-by=date|author`에서는 정렬 키에 hash를 **동률 처리 기준**으로 추가했다. 따라서 날짜가 같아도 hash가 다르면 hash 순서로 정렬된다. 이 점은 알고리즘 자체의 안정성과 구별해야 한다.

#### 3-5. 역색인은 왜 전체 순회보다 빠른가?

**전체 순회 검색:** 커밋이 V개라면 매번 V개 커밋의 메시지를 살펴본다. 메시지 길이 비교 비용을 단순화하면 O(V)이다.

**역색인 검색:** `login`이라는 단어가 가리키는 커밋 해시 목록을 딕셔너리로 바로 찾는다. 찾은 결과가 K개라면 목록을 출력하는 작업은 평균 O(K) 수준이다. 보통 K가 V보다 훨씬 작으면 유리하다.

그 대신 커밋을 만들 때 색인을 갱신해야 하고, 색인을 저장할 추가 메모리가 필요하다. **“검색 시간이 공짜”가 아니라, 등록·메모리 비용을 지불해 조회를 빠르게 만드는 설계**다.

### 항목 4. 요구사항 변경과 성능 개선 (4문항)

> 다음 4문항은 **현재 구현된 기능**이 아니라, 평가 질문에 대한 **예상 변화 및 개선 설계**를 설명한다. 개선 아이디어를 실제로 구현했다고 주장하지 않는다.

#### 4-1. 커밋이 10배 늘어나면 어디가 느려지고 어떻게 개선할까?

현재 `PATH`는 호출할 때마다 전체 커밋의 부모 연결을 읽어 **부모·자식 양방향 인접 목록**을 다시 만든다. 커밋이 많아질수록 이 부분이 반복 비용이 될 수 있다.

- **개선안 A — 인접 목록 유지:** `COMMIT` 시 부모·자식 인접 관계를 함께 갱신한다. 경로를 구할 때 그래프를 매번 새로 만드는 비용을 줄인다. 대신 메모리와 갱신 로직이 추가된다.
- **개선안 B — 탐색 결과 캐시:** 반복해서 요청되는 경로 또는 거리 정보를 저장한다. 다만 새 커밋이 생기면 기존 결과가 유효한지 확인하거나 캐시를 무효화해야 한다.
- **개선안 C — 규모가 큰 LOG:** DFS 방문에는 O(V+E), 전체 정렬에는 O(V log V)가 걸리고 전체 결과 문자열도 커진다. 필요한 구간만 보여주는 페이지네이션·출력 제한을 검토할 수 있다.
- **개선안 D — ANCESTORS:** 현재 조상 해시 정렬은 삽입 정렬이므로 조상이 많을 때 최악 O(A²)이 된다. 출력에 정렬이 반드시 필요하다면 직접 구현한 병합 정렬로 바꾸어 O(A log A)로 개선할 수 있다.

**평가용 한 문장:** “커밋 증가 시 PATH의 인접 목록 재구성, LOG 전체 출력과 정렬, ANCESTORS의 삽입 정렬이 부담이 될 수 있으므로 자료구조 유지·캐싱·효율적인 정렬로 개선하겠습니다.”

#### 4-2. PATH가 부모 방향만 허용한다면 어떻게 달라지나?

현재 무방향 PATH에서는 형제 커밋끼리 `B → A → C`로 이동할 수 있다. 하지만 **부모 방향만 허용**하면 B에서 A까지는 갈 수 있지만 **부모 A에서 자식 C로 내려갈 수 없다.**

```text
      A
     / \
    B   C

현재: PATH B C → B → A → C
부모 방향만: PATH B C → No path
부모 방향만: PATH B A → B → A
```

**변경할 코드:** `graph.py`의 `shortest_path()`에서 `adjacency[commit.hash].add(parent)`는 유지하고 **`adjacency[parent].add(commit.hash)`를 제거**하면 이동 가능한 방향이 부모 쪽으로만 제한된다. BFS와 경로 복원 구조는 그대로 사용할 수 있다.

단, 이 변경은 **현재 B5-2 미션의 무방향 PATH 요구사항과 다르므로 실제 코드는 수정하지 않았다.**

#### 4-3. LOG --sort-by=author도 부모가 자식보다 먼저여야 한다면?

작성자 이름만 단순 정렬하면 부모가 Zoe, 자식이 Alice인 경우 **Alice가 Zoe보다 먼저** 나올 수 있다. 이는 강화된 부모 우선 조건에 어긋난다.

**해결 전략:** **Kahn 위상 정렬 + 우선순위 큐**를 적용한다.

1. 각 커밋의 **진입차수**(아직 출력되지 않은 부모 수)를 계산한다.
2. 진입차수가 0인 커밋만 후보에 넣는다. 즉, **출력 가능한 커밋만** 모은다.
3. 후보 중 작성자 이름이 가장 앞서는 커밋을 꺼내 출력한다. 동률이면 hash를 비교한다.
4. 그 커밋의 자식들이 가진 미처리 부모 수를 1씩 줄인다. 0이 되면 후보에 넣는다.
5. 모든 커밋을 출력할 때까지 반복한다.

예를 들어 `Zoe(부모) → Alice(자식)`라면 작성자가 Alice여도 부모 Zoe가 먼저 출력되어야 한다. 형제처럼 부모 관계가 없는 커밋 사이에서는 작성자 기준을 적용할 수 있다.

**선택 이유:** “작성자 우선”이라는 선호를 **부모 우선이라는 필수 제약 안에서만** 적용하기 위해서다. 실제 구현 시에는 커밋에서 자식으로 향하는 인접 목록과 직접 구현한 최소 힙 또는 다른 우선순위 선택 로직이 필요하다.

**현재 코드와의 차이:** 현재 `mini_git.py`의 `log(sort_by="author")`는 일반 병합 정렬만 사용한다. **Kahn 기반 강화 방식은 설계안이며 구현되지 않았다.**

#### 4-4. 해시를 카운터 ↔ 난수 기반으로 바꾸면 무엇이 달라질까?

| 관점 | 현재: 카운터 기반 | 가정: 난수 기반 |
|---|---|---|
| 식별자 예시 | `00000001`, `00000002` | 예: `c8a7f2...` |
| 재현성 | 같은 생성 순서면 같은 번호 | 매번 달라질 수 있음 |
| 테스트 | 예상 hash를 직접 비교하기 쉬움 | 생성된 hash를 변수로 받아 비교하거나 난수 생성기를 고정·주입해야 함 |
| 디버깅 | 번호로 생성 순서를 추적하기 쉬움 | 번호에 생성 순서 정보가 없음 |
| 충돌 | 한 세션의 순차 번호에서는 원칙적으로 방지 | 난수 생성 후 기존 `commits` 키에 있는지 확인하고 충돌 시 재생성 필요 |
| 저장 후 재실행 | 카운터 복구가 필요 | 난수 충돌 검사와 저장된 커밋 조회가 필요 |

**개선 설계:** 해시 생성 코드를 별도 `generate_hash()` 함수 또는 주입 가능한 생성기 객체로 분리하면, 실서비스 모드와 테스트 모드의 생성 방식을 쉽게 바꿀 수 있다. 난수 기반 테스트에서는 길이·유일성 같은 **속성**을 확인하고, 필요한 경우 난수 생성기를 고정해 테스트를 재현한다.

**꼭 구분하기:** 실제 Git의 해시는 난수를 무작위로 선택하는 방식이 아니다. **커밋 내용과 메타데이터 등 객체 데이터에서 계산하는 콘텐츠 기반 해시**다. 따라서 난수 기반으로 바꾼다고 실제 Git 해시 방식과 같아지는 것은 아니다.

## 12. 제출 시 핵심 설명

Mini Git은 커밋을 **DAG**로 모델링하고, 각 커밋을 **딕셔너리**로 관리한다. `LOG`와 `ANCESTORS`는 **DFS**, `PATH`는 **BFS**, `SEARCH`는 **역색인**, `LOG --sort-by`는 내장 정렬 함수를 사용하지 않은 **병합 정렬**로 구현했다. 이를 통해 자료구조가 실제 개발 도구의 명령어 동작으로 연결되는 원리를 확인할 수 있다.
